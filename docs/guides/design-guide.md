# design-guide — 设计文档写作与评审规则

> 面向：模块设计者（人类成员）与其 Code Agent。
> 本文件回答：设计文档写什么、怎么组织、怎么同步、怎么被评审、冲突怎么办。

---

## 1. 流程与时序（两阶段 Issue）

```
1. 协调者发「阶段一：设计」Issue（方向 + 验收标准 + 边界）
2. 设计者领取 → 在 docs/design/<模块>/ 写设计（个人风格在此发挥）
3. 设计者发 PR → Agent 附 A 组自检表 → 协调者按 §8 评审方向
4. 合并 = 方案过线（方向锁定；再改方向 = 新 Issue）
5. 协调者发「阶段二：实现」Issue，需求依据 = 设计文档路径
6. 设计者的 Code Agent 领取 → 按阅读动线（根 AGENTS.md 起）读全上下文 → 实现
7. PR（附 A 组自检 + 自测报告）→ 非该模块成员 approve → squash 合并
8. Issue 自动关闭，设计文档按 §5 分档同步
```

微档小迭代（bugfix、小调整）可发**单阶段 fix Issue** 跳过设计阶段，分档见 §5。

## 2. 文档归属（谁写的东西放哪）

| 文档 | 作者 | 家在哪 | 什么时候存在 |
|---|---|---|---|
| Issue 正文（方向、边界、验收标准） | 协调者 | GitHub Issue | 任务起点 |
| 设计文档（个人风格与内容的载体） | 设计者 | `design/<模块>/` | 阶段一交付，实现前 |
| Agent 工作文档（任务拆解、实现计划） | 设计者 | 同上，模块文件夹内 | 实现期间 |
| PR 描述（实现报告） | 设计者 / Agent | GitHub PR | 实现之后 |
| 过程草稿（一次性） | 任何人 | `scratch/`（本地，不入库） | 随用随弃 |

原则：Issue 只放协调者的方向，模块文件夹放设计者的全部设计内容，PR 只放实现报告——三种内容各在各的领地。

## 3. 模块文件夹结构与设计文档模板

```
design/<模块名>/
├── README.md        # 登记索引：本模块所有文档一行一个
├── design.md        # 入口文档：概要设计（必写，阶段一交付物）
├── detail/          # 详细设计：api.md（对外 API 契约）与 data.md（实体 ER）
│                    #   ——阶段一固定交付物；ui.md 等按需
│                    #   单文件超 300 行按资源前缀/子模块拆目录（见下方约定）
├── archive/         # 被替代的旧设计（永不删除被引用的文档，见 §6）
└── （设计者自定的其他文件，如 plan.md，在 README 登记）
```

设计写到多细由协调者在阶段一评审把关（Issue 验收标准可要求补 detail）；实现中产生的真实技术决策按 §5 回流到 detail——详细设计的最后作者是 Code Agent，但落盘位置仍是模块文件夹。

detail 拆分约定：单文件触及 300 行上限时升级为目录，按资源前缀/子模块拆（如 `detail/api/题库.md`、`detail/data/题库.md`），文件名登记于 README——查找靠契约路由表与路径推导（codemap「查找动线」），不靠全文遍历。

**design.md 模板：**

```markdown
# <模块名> 设计文档

status: draft | active | deprecated
所属域: <!-- 9 域之一或平台底座 -->
维护者: <!-- 设计者 -->
关联 Issue: #<N>

## 1. 这个模块解决什么问题
<!-- 一段话；引用 Issue 验收标准 -->

## 2. 边界
- 对外提供：
- 依赖别人：
- 明确不做：

## 3. 概要设计
<!-- 结构、核心思路、关键决策；伪代码与接口签名可以，完整实现代码禁止 -->

## 4. 详细设计（固定落 detail/：api.md 对外契约、data.md 数据模型；其余按需）
<!-- 按需 -->

## 5. 验收对照
<!-- Issue 验收标准逐条：本设计如何覆盖 -->

## 6. 变更记录
| 版本 | 日期 | 变更 | 依据 |
```

## 4. 写作规则（八条）

1. **登记制**：每份文档必须在上级索引登记一行（codemap 登记顶层，blueprint/README 登记各域，模块 README 登记模块内文件）。未登记的文档等于不存在
2. **顶层封闭**：`docs/` 下的目录是封闭集合（product / architecture / design / guides + codemap.md），新增顶层 = Escalation
3. **命名固定**：设计文档永远是 `design/<模块>/design.md`，蓝图永远是 `blueprint/<域>.md`，detail 固定为 `api.md` / `data.md`（超限拆目录见 §3）——找文档靠路径推导，不靠搜索
4. **单文档 ≤ 300 行**：超了拆子文件，索引放 README
5. **索引与内容分离**：README / codemap 只放链接和一句话摘要，不放正文
6. **status 标记**：每份文档头部 `status: draft | active | deprecated`
7. **单一事实源（SSOT）**：同一事实只在一处定义，其他地方链接，禁止复制
8. **相对链接**：文档间引用一律用相对路径链接，禁止"见某某文档"式文字描述——死链是文档腐烂最早的可检测信号

## 5. 文档同步分档

判断只用**重实现测试**：*拿着现在的设计文档从头实现，会写出和改动后一致的代码吗？* 会 → 文档不动；不会 → 必须同步。

| 档位 | 典型场景 | Issue 形式 | 设计文档 | 契约 |
|---|---|---|---|---|
| 微：不触决策 | bugfix、日志、注释、命名、小重构 | 单阶段 fix | 不动 | 不动 |
| 中：行为变、结构不变 | 业务规则微调、接口加字段 | 单阶段 | 文档说到哪句改哪句 | 涉及 API 必须同步 |
| 大：结构与契约变 | 接口形状、表结构、模块边界 | 两阶段（设计先行） | 必须同 PR 同步 | 必须同步，可能 Escalation |

- 拿不准算哪档 → 按高一档处理
- 实现期 Agent 的文档改动限于「中档」以内；触碰大档 = 停下报告设计者
- 单个小改动合法跳过文档，积累的漂移由阶段审计兜底（见 §12）

## 6. 生命周期

- **废弃先沉底**：标 `deprecated` 并在索引沉底，满一个阶段无人引用再删
- **删除门禁**：被活代码引用的文档不许删，只能废弃；要删必须先删/改引用它的代码（同 PR）。检查可机械执行：`grep -r "docs/design/<模块>" --include="*.java"` 等按语言类推
- **重写不覆盖**：设计升级，旧版移入 `archive/`，路径永远可寻址
- **git 兜底**：真正漏网的，`git log --all --full-history -- <路径>` 找回任何历史版本
- 一句话原则：**代码的合法性来自自身与测试，文档链接只是出生证明**

## 7. 设计冲突解决

| 冲突类型 | 例子 | 裁判 | 结果归宿 |
|---|---|---|---|
| 数据所有权冲突 | 两个设计都声称拥有"成绩"表 | 协调者 | 写入 `contracts/data-ownership.md` |
| 接口交互冲突 | A 假设的 B 接口与 B 的设计不符 | 协调者 | 写入契约，或后合并的设计适配 |
| 共享底座/公共组件冲突 | 两个模块都想改底座迁就自己 | 协调者（底座领地） | 底座接受或拒绝 |
| 模块内风格差异 | 甲事件驱动，乙轮询 | 没人管——这是自由 | 无 |

- 判断口诀：**双方各自都没错但对不上 → 接缝问题 → 协调者；一方在自己模块内选了你不喜欢的方式 → 不是冲突 → 放行**
- 每次仲裁必须产出契约修订——同一冲突只允许发生一次
- 预防：共享接缝的模块，阶段一 Issue 串行发布，或先裁定接缝写入契约
- 检测点在阶段一评审（§8 B2），集成时发现等于失守；Agent 实现期嗅到冲突（如要用他域的表）= Escalation，禁止自行裁定

## 8. 方向评审标准（每项过/不过，无口味成分）

**A 组：机械合规项（Agent 预检，PR 附自检表）**

| # | 条款 | 判据 |
|---|---|---|
| A1 | 边界遵守 | 未触碰他域数据表（对照 data-ownership.md） |
| A2 | 契约遵守 | API 风格、错误模型符合 contracts/ |
| A3 | 只读区保护 | 未修改 reference/、core、铁律、契约 |
| A4 | 原创性 | 与 reference/ 示例无实质雷同 |
| A5 | 文档形态 | 符合模板、已登记、行数达标、无完整实现代码 |

**B 组：方向判断项（协调者判）**

| # | 条款 | 判据 |
|---|---|---|
| B1 | 主线贴合 | 与 Issue 验收标准逐条对应，无遗漏、无私自加戏（范围外的好想法 → 引导提提案） |
| B2 | 接缝一致 | 与已合并的相邻设计、契约层无冲突 |
| B3 | 依赖真实 | 声明的依赖存在且已就绪 |
| B4 | 可实现性 | 重实现测试：拿着设计能走出清晰的实现路径 |

**判定规则**：A 组任一不过 → 打回，理由只写条款号；B 组不过 → 打回附一句修改方向；全过 → 合并，方向锁定。异议仲裁在协调者，但双方必须引用条款说话——评审输出是"过/不过第几条"，不是"我觉得好不好"。

## 9. Issue 纪律（协调者发布规则，全员可见）

- 一个 Issue 一件事；验收标准写行为（给定 X 应得到 Y），不写感受
- 发布前必须指派 assignee——未指派的 Issue 等于不存在
- 一模块同时只有一个 open Issue
- 发布前自查依赖图无环（A 依赖 B、B 依赖 A = 全体死锁）
- 共享接缝的模块：阶段一串行发布，或先裁定接缝写入契约
- 超时回收：两周无进展（按阶段可调）评论催办，无响应收回重派，僵尸设计标 deprecated

## 10. 临时区（scratch/）与回流规则

`scratch/` 已 gitignore：不入库、不登记、不被引用、随时可删。其中结论若需存活必须回流 `design/` 或 Issue，默认死期是本次任务结束。判断标准：**需要另一个人（或另一个 Agent）看到的东西，就不该在 scratch 里。**

## 11. 阅读动线与行数预算

根 AGENTS.md + codemap + core + iron-laws 合计 ≤ 600 行——治理文件自身受"宪法克制"约束，超预算即违宪。任何往这四份文件加内容的提议，先删掉等长的旧内容。

## 12. 阶段审计（宪法与文档漂移的兜底机制）

「阶段」= 蓝图分期（一期~四期）。每期验收时，协调者执行一次阶段审计，清单：

1. **现实 ↔ 宪法冲突**：core.md 各条款与已合并的实现、文档有无矛盾。发现冲突且连续两个阶段未处理 → 触发 core.md §8 强制修宪议程
2. **文档漂移**：按 §5 重实现测试抽查设计文档与实现的一致性，漂移项责令同 PR 修复
3. **待决事项盘点**：蓝图「待决事项」与各契约 TODO-coordinator 条款的滞留时长，超两个阶段未动 → 升级处理或显式撤销

产出：审计结论写入当期验收记录；触发修宪的按 core.md §8 进流程。
