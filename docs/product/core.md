# core.md — 产品宪法

status: v0.7-draft（主线内容已填充，后续修订走 §8 修宪流程）

> 本文件定义本项目长期不变的主线。蓝图、设计、实现均不得违反本文件。
> 修改本文件 = 修宪，流程见 §8。除修宪外本文件只读。

## 1. 定位与边界

- 形态：K12 智慧教育平台，覆盖教、学、练、测、评全链路闭环
- 服务对象：K12 学校的学生、教师、家长、教务人员与校长
- 这个系统为谁解决什么问题：
  - **为学校**：搭建一个稳定运行的数字化学校底座，让教学过程数字化、可观测、可操作，成为 Agent 可以安全运行的环境
  - **为教师**：把备课、组题、组卷等重复性劳动交给 Agent——教师把自己对知识点的理解讲给 Agent，Agent 生成交互式课件（pptx / 可交互 HTML / 富文本）与分层练习；教师由此把精力还给课堂，专注通过知识点为学生讲透道理
  - **为学生**：因材施教——同一教学主线之下，每个学生获得适配自己的课程资料、练习题目与练习方式
  - **主线边界（铁律级）**：讲什么、练什么、考什么，主线始终由任课教师全权把控并负责；AI 生成内容分层生效——主线内容（课件上架、作业、试卷）须经教师确认，个性化补充层（变体讲解、拓展练习）免确认自动生效，但须标注 AI 生成、全程留痕、可随时关闭
- 明确不做：
  - AI 教学终审：所有 AI 产出皆为建议，课程/作业/考试/成绩等主线决策由任课教师全权把控
  - 校外培训机构业务形态：仅面向公立/私立学校校内场景（规避双减强监管）；公立形态裁剪招生与收费域
  - 自建重系统：直播课堂、网上阅卷等重系统不自建，采用外挂/外购/暂缓
  - 教育局级跨校平台：单校交付起步，预留对接接口但不做多校平台
- 建设次序（铁律级）：先建成数字化学校系统本体，待其稳定运行并投入实际生产一段时间后，方启动 Agent 运行时开发，顺序不可倒置；启动判据由蓝图定义、协调者裁定后生效；本阶段的交付物是「可观测、可运行」的环境（Agent-ready），不是 Agent

## 2. 角色与端

| 端 | 用户 | 使命 |
|---|---|---|
| 学生端 | 学生 | 因材施教的学习：主线课程与练习之上，获得 Agent 供给的个性化资料与练习（分层生效，见 §1） |
| 教师端 | 任课教师（含班主任视角） | 备课建课、作业与考试、批阅发布、依学情调整教学；班主任兼班级管理与家校沟通 |
| 家长端 | 家长 | 知情与协同：孩子学情可见、请假与沟通、缴费 |
| 教务管理端 | 教务人员 | 学校运营后台：招生分班、课表考务、学籍与成绩、教师工作量 |
| 校长端（全校数据总览） | 校长 | 全校学情总览、教学质量监控与决策支持 |
| 教室端（白板） | 设备身份常驻，教师扫码临时接入 | 授课运行时：课表定位、课件调用、板书与随堂互动 |

> 本表只锁使命；各端功能级场景清单见蓝图（角色体系与各域章节），场景迭代不动本文件。

## 3. 域判据（什么才配成为一个域）

同时满足以下三条才是域；否则是既有域内的子模块，走蓝图迭代，不动本文件：

1. **独立的数据所有权**：拥有自己负责的数据，不是别人数据的视图
2. **端到端的业务闭环**：从发起到完成不需要别的域替它收尾
3. **无法归入任何既有域**：归并优先于新增

加域 = 修宪事件，须对照三条判据论证。

## 4. 域清单（9 域 + 平台底座）

| 域 | 一句话职责 | 数据所有权核心 |
|---|---|---|
| 招生 | 线索/渠道 → 报名 → 入学测评（复用测评域）→ 录取分班；公立形态裁剪为报名录取 | 招生线索、报名与录取记录 |
| 课程（教） | 课程结构与知识点体系、课件资源（含授课运行时）、开班管理、课堂记录 | 课程/章/节/课时、知识点树、课件资源、课堂记录（板书） |
| 学习（学） | 学习过程（含课堂互动参与）、作业闭环、答疑讨论 | 学习记录（含课堂互动参与）、作业记录 |
| 测评（练测） | 题库、组卷、作业/测验/考试三形态、判分与成绩 | 题目、试卷、答题记录、成绩 |
| 学情与成长档案（评） | 学情分析、成长档案、学业预警 | 学情画像、成长档案、预警记录（源数据归源域） |
| 教务管理（管） | 校历课表、排课、考务编排、学籍异动、教师工作量 | 课表、学籍、考务编排 |
| 家校协同 | 通知公告、请假审批、沟通记录、学习报告推送 | 通知、请假与沟通记录 |
| 收费运营（营） | 账单、在线缴费、退费、续费提醒；公立形态裁剪为代收费务 | 账单与缴费记录 |
| 校园服务 | 行政办公（OA）、后勤事务（设施报修/巡检）、宿舍门禁与一卡通对接；五期按需，不阻塞教学主线 | 工单、公文与审批流程 |
| 平台底座 | 认证授权、组织架构、用户中心（含家长-学生绑定）、消息中心、文件服务、系统与设备管理 | 账号与权限、组织架构、家长-学生绑定关系、消息、文件元数据 |

> 数据所有权的权威清单在 `docs/architecture/contracts/data-ownership.md`，本表只做宪法层声明；修改本表必须同步该清单。

## 5. 模块间契约原则（骨架归协调者）

- 模块边界、数据所有权、认证模型、API 风格：由协调者定义（`contracts/`），所有人遵守
- 边界之内：设计者完全自由——风格、结构、实现路径均不受评审
- 模块之间不得直接访问对方数据表，只能通过契约接口

## 6. 技术基线

后端 Spring Boot（模块化单体）、前端 Vue 3；Agent 运行时 Python（独立进程，经契约 API 与业务单体交互，边界见 `architecture/contracts/agent-boundary.md`）。具体版本与选型清单以蓝图为准，其变更不构成修宪。

## 7. 质量底线

- 每个任务包交付的冒烟用例在单体启动后通过才可合并（冒烟清单随任务包交付）
- 契约先行：契约接口变更必须先改契约文档、同步所有消费方，再改代码
- AI 生成内容一律可追溯（Agent 标识 + 工具 + 参数留痕）；主线内容未经教师确认不得对学生可见
- AI 生成内容面向学生自动分发前须过内容护栏；对话式 AI 入口（答疑/导学）须完成合规验证后方可上线
- 未成年人敏感字段加密存储、展示脱敏，操作全程审计

## 8. 修宪流程

1. 提议：任何人可提议，附条款与现实冲突的证据
2. 论证：对照定位与域判据论证
3. 裁定与版本进位：协调者裁定后进位——MINOR（补内容）/ MAJOR（改主线），记录于下表
4. 强制触发器：阶段审计发现「现实与宪法冲突且连续两个阶段未处理」→ 强制进入修宪议程，改宪法或改现实，不许拖（阶段审计机制见 `guides/design-guide.md` §12）
