## 一、系统愿景与定位

以 **数字化学校系统** 为底座，将教育从线下转为线上，为 Agent 提供一个可以**观测和操作**的教育过程。

定位要点：

- **生产级、稳定的完整教育系统**——不是某个单一模块（如单独的考试系统），而是覆盖教、学、练、测、评、管、营全链路的平台
- **建设次序**：当前阶段只建数字化学校本体——为 Agent 提供可观测、可运行的环境；Agent 运行时开发在系统投入生产稳定运行一段时间后启动（宪法 §1 建设次序，详见 §十四）
- **面向 K12**：家长是一等公民、班主任是枢纽角色、教室是授课发生的物理场所
- 交付方式：团队不直接写代码，由项目负责人指导团队通过 **Code Agent** 交付，因此所有模块必须切分为边界清晰、可独立验收的任务包

## 二、总体架构：双运行时 × 四层全景

系统由两个对等运行时组成：**业务运行时（Spring Boot 模块化单体）是数字学校本体，Agent 运行时（Python）是大模型的运行与操作环境**——后者观测和操作前者，但不拥有前者的数据。交互收敛为三种模式（详细契约见 `architecture/contracts/agent-boundary.md`）：

```
┌────────────────────────┐              ┌────────────────────────┐
│ 业务运行时 = 世界        │              │ Agent 运行时 = 操作者    │
│ Spring Boot 模块化单体  │ ① 工具调用    │ Python                 │
│ · 8 业务域 + 平台底座    │ ◄─────────── │ · 编排与工具循环         │
│ · 业务事实的唯一属主     │              │ · 模型网关 / 记忆 RAG    │
│ · 权限/审计/事务的      │ ② 领域事件    │ · 安全护栏 / 评测 trace  │
│   确定性执行点          │ ───────────► │ （自有会话/向量库，       │
│ · 六端统一 API         │ ◄─③ 流式回传─ │   不建业务库）           │
└──────────┬─────────────┘              └────────────────────────┘
           │ 统一 API（REST / SSE / WebSocket）
           ▼
  ┌────────────────────────────────┐
  │ 用户触点层（6 个入口）           │
  │ 学生 / 教师 / 家长 / 教室端 /    │
  │ 教务 / 校长驾驶舱               │
  └────────────────────────────────┘
```

- ① Agent → 业务：同步工具调用 = 业务契约 API 的受控封装，双身份（服务 + 末端用户），写操作幂等
- ② 业务 → Agent：领域事件（作业提交、成绩发布、预警触发）驱动主动型 Agent（学情分析、周报、预警）
- ③ Agent → 前端：流式输出经业务网关转发，前端不直连 Agent 运行时

四层全景（业务运行时内部 + 共用基础设施）：**用户触点层**（6 入口，上图）→ **业务域层**（8 域，§五导航）→ **平台底座**（[blueprint/平台底座.md](blueprint/平台底座.md)）→ **基础设施层**（MySQL / Redis / 对象存储 / 任务调度 / 消息队列 / 监控与日志，§十三）。

认知锚点：**上层是"谁在用"，中层是"用什么"，底层是"凭什么稳定"**。底座没建好，上面八个域全是危楼。双运行时锚点：**业务单体是"世界"，Agent 运行时是"操作者"——世界不精确，操作者再聪明也不敢让它放手操作**。

## 三、角色体系

K12 的角色不是"学生 + 老师"这么简单，核心特征：**家长是一等公民**、**班主任是枢纽**、**教室端是唯一"设备身份 + 人的身份"双重入口**。

### 学生
- 学习中心：在学课程、继续学习、完成进度
- 学习行为：播放进度、笔记、收藏、提问讨论
- 作业：提交、查看批改结果、重做
- 测评：参加作业/测验/考试、查成绩、错题本、自主刷题
- 查看自己的学情画像与成长档案

### 任课老师
- 备课建课：课程结构（章/节/课时）、课件资源管理、知识点关联
- 备课建课（Agent 期）：向 Agent 描述知识点理解 → 生成交互式课件（pptx / 交互 HTML / 富文本）与分层练习 → 教师审定后挂课时
- 布置作业：布置 → 批改 → 打回重做
- 组卷发考：题库命题、组卷、发布考试、批阅主观题、发布成绩
- 学情查看：班级知识点掌握度、薄弱定位
- 教室端授课：扫码登录白板、调课件、板书、随堂互动

### 班主任
- 普通教师权限之外，是学生域和家校域的**交汇枢纽**：
- 班级管理：学生名单、班委、班级课表
- 家校沟通：面向家长发通知、审批请假
- 学业预警处理：接收进度落后/成绩下滑预警并跟进

### 家长
- K12 系统的口碑一半在家长体验上：
- 查看孩子：学习进度、成绩报告、课表、课堂记录（板书）
- 家校协同：接收通知、发起请假、沟通记录
- 缴费：账单、在线缴费、退费
- 关键数据关系：**家长与学生是多对多绑定**（一个家长多个孩子、一个孩子多个监护人），从招生/入学建立，贯穿缴费、通知、报告所有场景

### 教务管理员
- 系统的"运营中枢"：录取分班、排课课表、考务编排、成绩管理、学籍异动（转班/休学/结业）、教师工作量

### 系统管理员
- 账号、权限（RBAC 到菜单/按钮级）、参数、字典、审计日志

### 教室端（白板）
- 触点层的第 5 个入口，唯一**以设备身份为主、教师身份为辅**的入口：白板是"常驻居民"（设备账号），教师是"临时访客"（扫码进来、下课即走）。详见 [blueprint/教室端.md](blueprint/教室端.md)

## 六、核心数据模型：主链与支链

把系统抽象成一条主链，所有功能都是在这条链上做加法：

```
学生 ∈ 班级 —任课→ 教师 —讲授→ 课程 —覆盖→ 知识点 ←标注— 题目
```

三条支链（学习支链挂课时、测评支链挂题目、家校支链挂学生-家长绑定与成长档案）。关系骨架 ER、ID 契约（属主生成、他域只引用）、课表五要素的 **SSOT 在 [global-data-model](../architecture/contracts/global-data-model.md)**，各域表级设计归域设计文档。主链 ID 体系是所有域共享的契约——这也是底座必须先行的原因。

## 七、核心业务流程（4 条主流程 + 1 条课堂时间线）

**教师主流程**：备课建课 → 关联知识点 → 开班 → 指定学员 → 授课（教室端）→ 布置作业 → 组卷发考 → 批阅主观题 → 发布成绩 → 查看学情 → 调整教学

**学生主流程**：入学分班 → 进入学习中心 → 逐课时学习（记笔记、提问）→ 交作业 → 参加考试 → 查成绩 → 错题重练 → 复盘提升

**考试主流程**：命题入库 → 组卷 → 发布考试 → 答题（乱序/倒计时/防切屏）→ 交卷（幂等/自动交卷兜底）→ 判分 → 发布 → 试卷分析

**管理者主流程**：招生/导入学员 → 分班排课 → 过程监控（进度/预警）→ 结业报表 → 数据决策

**教室端课堂时间线**：
1. 上课前 1 分钟：白板常驻，按课表时段自动唤醒，显示二维码
2. 扫码登录：教师手机端扫码免密登录；白板从课表得知：当前时段 + 本教室 + 班级 + 课程 + 教师
3. 调课件：点"开始上课"，挂在课时下的资源包自动从云端拉取——**课件在课时上，不在 U 盘里**
4. 授课中：演示课件、电子白板板书、学科工具、随机点名、计时器
5. 随堂互动：推题到学生端，实时收回，白板当场展示正确率分布
6. 下课：板书保存为课堂记录（学生端可回看）；教师登出或超时自动登出，白板回到待机界面

## 八、业务闭环（系统的灵魂）

1. **教学质量闭环**：教 → 学 → 练 → 测 → 学情数据 → 反哺教学调整。教室端加入后，数据起点从**课后提前到课中**（板书、互动、随堂测回流）
2. **学生成长闭环**：学 → 练 → 测 → 错题 → 针对性补弱 → 再测验证。错题本和知识点掌握度是枢纽
3. **试题质量闭环**：命题 → 考试使用 → 统计难度/区分度 → 淘汰劣质题、优化题库。题库越用越准，是长期资产
4. **家校共育闭环**（K12 特有）：课堂表现/成绩/预警 → 自动推送家长 → 家长督促反馈 → 教师掌握家庭侧情况 → 调整教学。家长是闭环的参与者，不是旁观者
5. **招生-交付-口碑闭环**（机构定位）：招生 → 分班交付 → 教学质量 → 家长满意度 → 续费/转介绍 → 反哺招生

前三条是任何定位都成立的核心，后两条按定位裁剪。

## 九、行业"XX 系统"与本项目模块的对照

教育信息化行业在每个节点都沉淀了独立系统（学校过去一个个单独采购）。自建时的对应关系：

> **行业里的"一个系统" = 本项目框架里"一个域内的模块"**

不是做二三十个独立系统，而是按八域聚合在一个应用里，保持模块边界清晰。主链各节点与行业系统的对照清单已随迁移写入各分域蓝图的「行业对照」与「接缝」小节。

课件与题库本质都是教学资源（一个挂课时、一个挂知识点），管理形态高度相似（上传/导入、审核、共享、版本、引用）——资源层可设计成**一套通用资源管理骨架**，课件和题目是其上的实例。

优先级：落在主链闭环上的模块（学籍、课程+课件、题库、学习、考试、成绩分析、家校）是必做主干；听评课、德育积分、驾驶舱大屏属于可后置增强项。

**三个"重系统"例外**（技术上不是普通 CRUD，如做需单独评估）：直播课堂（流媒体）、网上阅卷（扫描硬件耦合）、排课（约束求解算法）。

## 十、全局架构决策：模块化单体，而非多系统整合

**决策**：主干八域自建，走**按域分模块的模块化单体**（Maven 多 module）；直播、网上阅卷、Agent 运行时（Python）作为"特种兵"独立外挂，挂到统一身份和消息机制上，主干数据模型仍然只有一份。

**本质区别**：多系统整合的集成发生在**运行时**（网络调用、消息、数据同步，一致性靠事后对齐）；模块拆分的集成发生在**进程内**（接口调用、编译期约束，一致性靠事务）。

**反例场景（学生从 3 班转 5 班）**：
- 模块化单体：一个事务改一条记录，所有模块读同一行数据，瞬间一致
- 二十个独立系统：学籍改完要通过消息/同步通知学习、考试、缴费、家校平台……同步窗口内孩子在旧班考试、账单发给旧班主任。需要消息重试、对账、补偿、人工修数，乘以所有需同步的数据 = 集成地狱（N 个系统 ≈ N×(N-1)/2 量级接口对接）

**防腐蚀铁律**（模块化单体成立的前提）：每张表有唯一属主模块，别的模块不许直接查，只能走属主暴露的接口；模块间依赖单向；用 ArchUnit 在 CI 自动检查。此纪律写入 Code Agent 任务包验收标准。

**两种失败形态**：多系统做砸 = 分布式单体（两头缺点全占，最隐蔽的 bug 是"偶现数据不一致"）；模块化做砸 = 大泥球（互查对方表，边界名存实亡）。

**演进保险**：现在画的模块边界 = 将来拆微服务的缝。考试域并发真需要独立伸缩时沿边界抽出即可；反过来从二十个系统往回合拢，实践中几乎不可能。

**Agent 运行时 = 第三个特种兵**：与直播（流媒体）、网上阅卷（扫描硬件）同理，它技术上必须独立——LLM 生态 Python-first、伸缩与发版节奏独立、故障域需隔离，符合"只有技术上必须分开的才付分布式成本"的判据。外挂纪律对它同样生效：**无业务库，一切读写经业务契约 API**（边界见 `architecture/contracts/agent-boundary.md`），Agent 只是契约接口的又一个消费者（服务身份 + 末端用户身份）——防腐蚀铁律不因消费方是 AI 而豁免。

**原则一句话**：能在一个事务里解决的耦合，就不要推到网络上去解决；只有在技术上必须分开的，才值得为它付分布式的成本。

## 十二、合规与安全红线（K12 生产级不可回避）

- **未成年人个人信息保护**：收集学生信息需监护人同意、最小化收集、敏感字段（姓名/身份证/成绩）加密存储、展示脱敏、导出留痕
- **权限最小化 + 全程审计**：谁能看哪些学生的数据，逐层收口
- **内容合规**：题库/课件审核机制后才可上架
- **等保备案**（二级起步）：真实对外运营的硬门槛
- **定位分叉（已决 2026-09-09）**：仅面向公立/私立学校校内场景，不做校外培训机构业务形态（双减强监管规避，宪法 §1 明确不做）。公立形态裁剪招生/收费域；教育局对接预留接口但不在范围内（宪法：不做跨校平台）

## 十三、技术底座与生产工程

**后端**：Spring Boot 3 + JDK 17，按域分模块的单体（Maven 多 module，预留微服务演进）；MyBatis-Plus；Spring Security + JWT；Redis（会话/幂等/热点）；MySQL 8；Knife4j；任务调度（自动交卷、定时发布）；WebSocket（随堂测、监考消息、站内通知）。

**前端**：Vue 3 + TypeScript + Pinia + Element Plus；拆**学生端**与**管理端（教师/教务/管理员）**两个应用 + **Web 教室端**大屏应用；ECharts 做报表。

**Agent 运行时（Python）**：Python 3.12+、FastAPI + Pydantic；编排框架选型待评（LangGraph / OpenAI Agents SDK / 自研工具循环）；模型接入经统一模型网关（多模型可切换、可降级）；记忆与 RAG 用运行时自有向量存储（Qdrant / pgvector 待评），不进业务 MySQL；trace 与评测用 Langfuse（或同类）；流式输出 SSE。与业务单体只经 agent-boundary 契约交互（铁律 L8）。

**视频**：接云点播或 MinIO + 转码，不自建转码。

**生产工程**：多环境配置、日志链路 traceId、监控告警（Prometheus + Grafana）、数据库备份、压测、CI/CD、Docker Compose 起步。

**契约先行**：先产出全局数据模型与各域 API 契约，再分包实现——避免多个 Agent 各造轮子。落位：全局主链骨架与 ID 契约在 [global-data-model](../architecture/contracts/global-data-model.md)、API 风格与错误码在 [api-conventions](../architecture/contracts/api-conventions.md)、数据属主在 [data-ownership](../architecture/contracts/data-ownership.md)；**各域实体 ER 与对外 API 契约随阶段一设计落 `docs/design/<域>/`**（`detail/data.md`、`detail/api.md`，模块 README 登记），跨域消费以属主域设计文档为权威。查找动线（路由表 → 路径推导 → 索引）见 [codemap](../codemap.md)。

分期之上有两大建设阶段（宪法 §1 建设次序）：

1. **数字化学校建设期（当前阶段 = 一期~四期全部）**：只建业务运行时（Spring Boot 模块化单体 + 六端），不开发 Agent 运行时。本阶段的隐性验收标准是 **Agent-ready**——领域事件外发、契约 API 完备、写操作幂等、审计齐备，让未来的 Agent 可观测、可操作
2. **Agent 建设期（前置条件：系统稳定运行并投入实际生产一段时间）**：启动 Python Agent 运行时开发；学生端先以后台引擎形态落地（个性化资料/练习，静默生效、标注 AI 生成、留痕可关闭），对话式入口（AI 答疑/导学）待内容护栏与合规验证后引入

## 十五、Code Agent 交付切分原则

- **契约先行**：全局 ER 模型 + 各域 API 契约先定，再分包实现（落位见 §十三）
- **任务包边界 = 域内模块边界**：如"题库管理""作业闭环""学习中心"各自独立任务包，可单独验收
- **底座单独一个任务包且最先完成**，后续所有包依赖它的登录态、权限、统一响应规范
- **验收标准写进任务书**：接口清单 + 页面清单 + 验收用例
- **模块边界纪律进验收标准**（表属主、单向依赖、ArchUnit 检查），防止 Agent 挖墙脚
- 胶水层（适配器/同步/对账）最难测试最难验收——架构上尽量避免出现（见"模块化单体"决策）
- **Agent 建设期：运行时单独成包且先于一切 AI 能力交付**（本体：编排 / 工具注册 / 模型网关 / 记忆，依赖底座契约）；各 AI 能力（课件与分层练习生成、批改建议、学情周报、学业预警）各自独立任务包，同时依赖运行时与对应业务域契约。建设期启动前置条件见 §十四
