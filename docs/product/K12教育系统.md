## 一、系统愿景与定位

以 **数字化学校系统** 为底座，将教育从线下转为线上，为 Agent 提供一个可以**观测和操作**的教育过程。

定位要点：

- **生产级、稳定的完整教育系统**——不是某个单一模块（如单独的考试系统），而是覆盖教、学、练、测、评、管、营全链路的平台
- **面向 K12**：家长是一等公民、班主任是枢纽角色、教室是授课发生的物理场所
- 交付方式：团队不直接写代码，由项目负责人指导团队通过 **Code Agent** 交付，因此所有模块必须切分为边界清晰、可独立验收的任务包

## 三、角色体系

K12 的角色不是"学生 + 老师"这么简单，核心特征：**家长是一等公民**、**班主任是枢纽**、**教室端是唯一"设备身份 + 人的身份"双重入口**。

### 学生
- 学习中心：在学课程、继续学习、完成进度
- 学习行为：播放进度、笔记、收藏、提问讨论
- 作业：提交、查看批改结果、重做
- 测评：参加作业/测验/考试、查成绩、错题本、自主刷题
- 查看自己的学情画像与成长档案

### 任课老师
- 备课建课：课程结构（章/节/课时）、课件资源管理、知识点关联
- 布置作业：布置 → 批改 → 打回重做
- 组卷发考：题库命题、组卷、发布考试、批阅主观题、发布成绩
- 学情查看：班级知识点掌握度、薄弱定位
- 教室端授课：扫码登录白板、调课件、板书、随堂互动

### 班主任
- 普通教师权限之外，是学生域和家校域的**交汇枢纽**：
- 班级管理：学生名单、班委、班级课表
- 家校沟通：面向家长发通知、审批请假
- 学业预警处理：接收进度落后/成绩下滑预警并跟进

### 家长
- K12 系统的口碑一半在家长体验上：
- 查看孩子：学习进度、成绩报告、课表、课堂记录（板书）
- 家校协同：接收通知、发起请假、沟通记录
- 缴费：账单、在线缴费、退费
- 关键数据关系：**家长与学生是多对多绑定**（一个家长多个孩子、一个孩子多个监护人），从招生/入学建立，贯穿缴费、通知、报告所有场景

### 教务管理员
- 系统的"运营中枢"：录取分班、排课课表、考务编排、成绩管理、学籍异动（转班/休学/结业）、教师工作量

### 系统管理员
- 账号、权限（RBAC 到菜单/按钮级）、参数、字典、审计日志

### 教室端（白板）
- 触点层的第 5 个入口，唯一**以设备身份为主、教师身份为辅**的入口：白板是"常驻居民"（设备账号），教师是"临时访客"（扫码进来、下课即走）。详见"教室端专题"

## 五、业务域全景（8 域 + 底座）

**0. 平台底座（必须先行，贯穿所有域）**
- 认证授权：登录态、RBAC（学生/教师/班主任/教务/管理员/家长）、操作审计
- 组织架构：机构 → 校区 → 学部（小/初/高）→ 年级 → 班级；教师归属与任课关系
- 用户中心：各类角色档案、批量导入、账号生命周期
- 消息中心：站内信、公告、通知（邮件/短信/微信渠道预留）
- 文件服务：视频、图片、课件的上传与存储（接 MinIO 或云 OSS）
- 系统管理：数据字典、参数配置、登录/操作日志
- 设备管理：教室白板设备的注册绑定、心跳监控、远程运维
- 工程规范：统一响应与异常、参数校验、接口文档（Knife4j）——团队协作交付的地基

**1. 招生域**：招生线索/渠道 → 报名 → 入学测评（复用测评域）→ 录取 → 分班。机构的命脉，公立校可裁剪为报名录取。

**2. 课程域（教）**：
- 课程按**学段 × 学科 × 教材版本**（人教版等）三维组织——K12 特有的分类骨架，题库标注维度必须与之对齐，否则学情分析无从谈起
- 课程结构：课程 → 章 → 节 → 课时（视频/图文/课件）；知识点树挂章节
- 课件管理系统属于本域的**资源子层**，与题库互为"孪生兄弟"（见"行业系统对照"）
- 开班管理：课程实例化为教学班（讲师 + 学员名单 + 起止时间 + 学习计划）

**3. 学习域（学）**：分班指派课程 → 学习中心（进度/续学）→ 学习行为记录（防挂机、笔记）→ 作业闭环（布置→提交→批改→打回）→ 答疑讨论。

**4. 测评域（练测）**：
- 题库：五种题型（单选/多选/判断/填空/简答）、按知识点/难度归类、Excel 批量导入
- 组卷：手动选题 + 随机抽题（按题型/难度/知识点，可每人卷面不同）
- 三种形态：**作业**（不计时）、**测验**（随堂实时，含教室端推送）、**考试**（正式：防作弊 + 断线续答 + 自动交卷）
- 判分：客观题自动、主观题教师批阅、成绩发布与复核；K12 追加年级/班级排名与历次纵向追踪
- 错题本、自主刷题、试卷分析
- 生产级技术要点：考试状态机（Redis 会话）、交卷幂等、批量判分异步化、延迟任务自动交卷、防切屏留痕

**5. 学情与成长档案域（评）**：
- 学情分析：知识点掌握度雷达、班级/年级对比、薄弱定位
- 学生成长档案（K12 特色）：综合素质记录、奖惩、德育积分、教师评语——过程性数据的长期沉淀
- 学业预警：进度落后/成绩下滑 → 自动推给教师和家长

**6. 教务管理域（管）**：校历课表、排课（走班选科可选）、考务编排、学籍异动、教师工作量、管理驾驶舱。

**7. 家校协同域**：通知公告（按班级/年级定向触达家长）、请假审批（家长发起→班主任审批）、家校沟通记录、家长会管理、**每周/每学期孩子学习报告自动推送**。

**8. 收费运营域（营）**：学费账单、在线缴费、退费、续费提醒（机构核心；公立校裁剪为代收费务）。

## 六、核心数据模型：主链与支链

把系统抽象成一条主链，所有功能都是在这条链上做加法：

```
学生 ∈ 班级 —任课→ 教师 —讲授→ 课程 —覆盖→ 知识点 ←标注— 题目
```

三条支链都挂在主链上：

1. **学习支链**：课程 → 课时 → 学习记录（学生侧过程数据）
2. **测评支链**：题目 → 试卷 → 考试 → 答题记录 → 成绩 → 学情报告（测评侧结果数据）
3. **家校支链**：学生 —绑定→ 家长（家校与付费的锚点）；学生 → 成长档案（时间维度沉淀）

两个关键建模契约：

- **课表五要素**：一节课 = 时间 + 班级 + 课程 + 教师 + **教室**。K12 现实是班级固定教室、教师走班，教室-班级有常驻绑定，教师-教室通过课表发生临时关系。教室端的一切智能建立在五要素模型上
- **主链 ID 体系**（学生/班级/课程/知识点的全局唯一）是所有域共享的契约，这也是底座必须先行的原因

## 七、核心业务流程（4 条主流程 + 1 条课堂时间线）

**教师主流程**：备课建课 → 关联知识点 → 开班 → 指定学员 → 授课（教室端）→ 布置作业 → 组卷发考 → 批阅主观题 → 发布成绩 → 查看学情 → 调整教学

**学生主流程**：入学分班 → 进入学习中心 → 逐课时学习（记笔记、提问）→ 交作业 → 参加考试 → 查成绩 → 错题重练 → 复盘提升

**考试主流程**：命题入库 → 组卷 → 发布考试 → 答题（乱序/倒计时/防切屏）→ 交卷（幂等/自动交卷兜底）→ 判分 → 发布 → 试卷分析

**管理者主流程**：招生/导入学员 → 分班排课 → 过程监控（进度/预警）→ 结业报表 → 数据决策

**教室端课堂时间线**：
1. 上课前 1 分钟：白板常驻，按课表时段自动唤醒，显示二维码
2. 扫码登录：教师手机端扫码免密登录；白板从课表得知：当前时段 + 本教室 + 班级 + 课程 + 教师
3. 调课件：点"开始上课"，挂在课时下的资源包自动从云端拉取——**课件在课时上，不在 U 盘里**
4. 授课中：演示课件、电子白板板书、学科工具、随机点名、计时器
5. 随堂互动：推题到学生端，实时收回，白板当场展示正确率分布
6. 下课：板书保存为课堂记录（学生端可回看）；教师登出或超时自动登出，白板回到待机界面

## 八、业务闭环（系统的灵魂）

1. **教学质量闭环**：教 → 学 → 练 → 测 → 学情数据 → 反哺教学调整。教室端加入后，数据起点从**课后提前到课中**（板书、互动、随堂测回流）
2. **学生成长闭环**：学 → 练 → 测 → 错题 → 针对性补弱 → 再测验证。错题本和知识点掌握度是枢纽
3. **试题质量闭环**：命题 → 考试使用 → 统计难度/区分度 → 淘汰劣质题、优化题库。题库越用越准，是长期资产
4. **家校共育闭环**（K12 特有）：课堂表现/成绩/预警 → 自动推送家长 → 家长督促反馈 → 教师掌握家庭侧情况 → 调整教学。家长是闭环的参与者，不是旁观者
5. **招生-交付-口碑闭环**（机构定位）：招生 → 分班交付 → 教学质量 → 家长满意度 → 续费/转介绍 → 反哺招生

前三条是任何定位都成立的核心，后两条按定位裁剪。

## 九、行业"XX 系统"与本项目模块的对照

教育信息化行业在每个节点都沉淀了独立系统（学校过去一个个单独采购）。自建时的对应关系：

> **行业里的"一个系统" = 本项目框架里"一个域内的模块"**

不是做二三十个独立系统，而是按八域聚合在一个应用里，保持模块边界清晰。主链各节点的对照：

| 主链节点 | 行业中的独立系统 |
|---|---|
| 学生 | 学籍管理、成长档案、综合素质评价、考勤请假 |
| 班级 | 班级管理、德育量化考核 |
| 教师 | 教师管理（人事/工作量）、集体备课教研、听评课 |
| **课程** | **课件管理（资源子层）**、教学资源库、课程管理 |
| 任课关系 | 排课系统、考务系统 |
| 知识点 | 知识图谱管理（通常内嵌，不独立；学情分析命脉） |
| 题目 | 题库系统（与课件同属资源层孪生兄弟） |
| 学习支链 | 在线学习平台、作业系统、直播课堂、答疑讨论、错题本 |
| 测评支链 | 组卷、在线考试、网上阅卷（答题卡+流水阅卷）、成绩分析 |
| 家长支链 | 家校沟通平台、缴费系统、学习报告推送 |
| 底座 | 统一身份认证 SSO、组织架构、消息中心、校园网盘、审计 |

课件与题库本质都是教学资源（一个挂课时、一个挂知识点），管理形态高度相似（上传/导入、审核、共享、版本、引用）——资源层可设计成**一套通用资源管理骨架**，课件和题目是其上的实例。

优先级：落在主链闭环上的模块（学籍、课程+课件、题库、学习、考试、成绩分析、家校）是必做主干；听评课、德育积分、驾驶舱大屏属于可后置增强项。

**三个"重系统"例外**（技术上不是普通 CRUD，如做需单独评估）：直播课堂（流媒体）、网上阅卷（扫描硬件耦合）、排课（约束求解算法）。

## 十、全局架构决策：模块化单体，而非多系统整合

**决策**：主干八域自建，走**按域分模块的模块化单体**（Maven 多 module）；直播、网上阅卷作为"特种兵"独立外挂，挂到统一身份和消息中心上，主干数据模型仍然只有一份。

**本质区别**：多系统整合的集成发生在**运行时**（网络调用、消息、数据同步，一致性靠事后对齐）；模块拆分的集成发生在**进程内**（接口调用、编译期约束，一致性靠事务）。

**反例场景（学生从 3 班转 5 班）**：
- 模块化单体：一个事务改一条记录，所有模块读同一行数据，瞬间一致
- 二十个独立系统：学籍改完要通过消息/同步通知学习、考试、缴费、家校平台……同步窗口内孩子在旧班考试、账单发给旧班主任。需要消息重试、对账、补偿、人工修数，乘以所有需同步的数据 = 集成地狱（N 个系统 ≈ N×(N-1)/2 量级接口对接）

**防腐蚀铁律**（模块化单体成立的前提）：每张表有唯一属主模块，别的模块不许直接查，只能走属主暴露的接口；模块间依赖单向；用 ArchUnit 在 CI 自动检查。此纪律写入 Code Agent 任务包验收标准。

**两种失败形态**：多系统做砸 = 分布式单体（两头缺点全占，最隐蔽的 bug 是"偶现数据不一致"）；模块化做砸 = 大泥球（互查对方表，边界名存实亡）。

**演进保险**：现在画的模块边界 = 将来拆微服务的缝。考试域并发真需要独立伸缩时沿边界抽出即可；反过来从二十个系统往回合拢，实践中几乎不可能。

**原则一句话**：能在一个事务里解决的耦合，就不要推到网络上去解决；只有在技术上必须分开的，才值得为它付分布式的成本。

## 十一、教室端（白板）专题

**定位**：触点层第 5 个入口；教室成为教务域一等实体（课表五要素）；课件管理系统从"资源库"升级为"授课运行时"。

**功能模块**：
- 身份与登录：扫码免密登录（教师手机端扫白板二维码）、超时自动登出、下节课教师无缝交接
- 课表感知：按 教室 + 当前时间 自动定位当节课；显示今日本教室课表
- 课件运行时：拉取"课时-资源包"，视频流式播放不整包下载
- 电子白板：多点书写、多页板书、板书保存为课堂记录挂到课时
- 课堂工具：随机点名、抢答、计时器、聚光灯、学科工具（几何/函数图像）
- 随堂测验：题目推送、实时收回（WebSocket）、当场统计展示——测评域"测验"形态的课堂实时版
- 弱网兜底：当天课件本地预缓存，断网也能上课

**对已有模块的涟漪**：
1. 课件管理系统：新增"课时-资源包"概念与预缓存策略
2. 排课模型：教室成为一等公民，建教室-班级常驻绑定
3. 测评域：随堂测验成为第三个消费场景，需 WebSocket 实时通道
4. 合规：课堂实录录课涉及学生肖像声音，监护人同意 + 严格权限——红线项，一期不做

**技术现实约束**：
- 教室大屏（希沃/鸿合/MAXHUB）主流 Android，部分带 Windows OPS 模块
- 最现实路径：**Web 版教室端**（Vue 3 大屏适配）跑在大屏浏览器或 OPS Chrome 里，复用全栈技术栈；板书用 Canvas 成熟手写库
- 交互规范：触摸优先（大按钮）、无 hover、无键盘（登录全靠扫码）、16:9 横屏常亮

**Code Agent 交付切分**：① 后端支撑（资源包 API、扫码登录、课堂记录、随堂测 WebSocket 通道）② Web 教室端（依赖①契约）③ 设备管理（心跳/远程指令）。电子白板书写体验（手写延迟、笔迹平滑）是 Agent 交付质量洼地，必须用成熟库。

## 十二、合规与安全红线（K12 生产级不可回避）

- **未成年人个人信息保护**：收集学生信息需监护人同意、最小化收集、敏感字段（姓名/身份证/成绩）加密存储、展示脱敏、导出留痕
- **权限最小化 + 全程审计**：谁能看哪些学生的数据，逐层收口
- **内容合规**：题库/课件审核机制后才可上架
- **等保备案**（二级起步）：真实对外运营的硬门槛
- **定位分叉（待决）**：公立/私立学校校内使用 vs 校外培训机构。后者受双减政策强约束（学科类培训的资质、时间、收费监管），业务范围要提前规避；校内使用无此问题，但可能涉及教育局系统对接

## 十三、技术底座与生产工程

**后端**：Spring Boot 3 + JDK 17，按域分模块的单体（Maven 多 module，预留微服务演进）；MyBatis-Plus；Spring Security + JWT；Redis（会话/幂等/热点）；MySQL 8；Knife4j；任务调度（自动交卷、定时发布）；WebSocket（随堂测、监考消息、站内通知）。

**前端**：Vue 3 + TypeScript + Pinia + Element Plus；拆**学生端**与**管理端（教师/教务/管理员）**两个应用 + **Web 教室端**大屏应用；ECharts 做报表。

**视频**：接云点播或 MinIO + 转码，不自建转码。

**生产工程**：多环境配置、日志链路 traceId、监控告警（Prometheus + Grafana）、数据库备份、压测、CI/CD、Docker Compose 起步。

**契约先行**：先产出全局数据模型（ER）与各域 API 契约，再分包实现——避免多个 Agent 各造轮子。

## 十五、Code Agent 交付切分原则

- **契约先行**：全局 ER 模型 + 各域 API 契约先定，再分包实现
- **任务包边界 = 域内模块边界**：如"题库管理""作业闭环""学习中心"各自独立任务包，可单独验收
- **底座单独一个任务包且最先完成**，后续所有包依赖它的登录态、权限、统一响应规范
- **验收标准写进任务书**：接口清单 + 页面清单 + 验收用例
- **模块边界纪律进验收标准**（表属主、单向依赖、ArchUnit 检查），防止 Agent 挖墙脚
- 胶水层（适配器/同步/对账）最难测试最难验收——架构上尽量避免出现（见"模块化单体"决策）
